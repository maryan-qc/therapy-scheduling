# 0001. Доступ терапевта до карток клієнтів — RLS із функцією «свій клієнт» у базі

- Статус: прийнято
- Дата: 2026-10-23
- AC: AC-CARD-04, AC-CARD-05, AC-CARD-07, AC-CARD-08, AC-CARD-09, AC-CARD-10, AC-CARD-11

## Контекст

Зріз 2 (`openspec/specs/client-cards`, вимога PM Sofiia-pm/therapy-scheduling-spec#19) дає терапевту список і
картки лише **своїх** клієнтів — тих, у кого з ним є утримання «Held» (ще не прострочене) або сеанс «Confirmed».
Щойно утримання прострочилося, картка для терапевта недоступна (AC-CARD-08). Чужа картка за прямим посиланням —
«You don't have access to this client.» без жодних даних (AC-CARD-05). Планувальник і адміністратор бачать усі
картки (AC-CARD-10), користувач без ролі й відвідувач без входу — жодної (AC-CARD-07, AC-CARD-11).

Обмеження:

- «Свій» залежить від часу: утримання стає «Expired» рівно через 1440 хвилин без фонової задачі (припущення PM,
  тариф Vercel Hobby — cron щонайбільше раз на добу).
- Застосунок читає дані через Supabase Data API з токеном користувача. Ключ `publishable` публічний, тож будь-хто з
  токеном терапевта може робити запити до `/rest/v1/clients` в обхід наших сторінок.
- Відгук викладача до WS6 знайшов саме таку діру: сторінка `/schedule` ховала прострочені утримання, а база віддавала
  їх разом з email клієнта (виправлено міграцією `20261023084029`).

## Рішення

Правило «свій клієнт» живе в базі, і його застосовує RLS:

- `private.is_client_of_current_therapist(client_id)` — `security definer`, `set search_path = ''`: є утримання
  чи сеанс цього клієнта на слотах поточного терапевта, і воно підтверджене або ще не прострочене (`now()`).
- `clients_select`: `is_staff()` або `is_client_of_current_therapist(id)`; `holds_select` — та сама умова статусу.
- `private.current_therapist_id()` визначає терапевта лише для ролі `therapist` (міграція `20261023105250`), тож
  користувач без ролі не стає терапевтом навіть зі збігом email.
- Для `update` і `delete` на `clients` GRANT немає, тож картку не змінити (AC-CARD-05, AC-CARD-07, AC-CARD-11 — «картка
  не змінилася»). `anon` — `revoke all`.
- Сторінки `/clients` і `/clients/[id]` нічого не фільтрують самі: показують те, що віддала база. Порожня відповідь
  для терапевта означає «You don't have access to this client.» — однаково для чужої й неіснуючої картки.
- Admin-клієнта (`SUPABASE_SECRET_KEY`) застосунок не використовує.

## Розглянуті варіанти

- **Фільтр у Server Action чи сторінці** (читати всі картки й відкидати чужі в коді). Ні: Data API лишається
  відкритим для токена терапевта, і будь-яка нова сторінка чи запит мусить повторити фільтр. Саме так виникла діра
  WS6.
- **Окрема view `my_clients` з умовою в `where`**. Ні: view в `public` за замовчуванням виконується з правами
  власника (обходить RLS таблиці), тож потрібні `security_invoker` і ті самі політики. Виходить друге місце правила
  без виграшу.
- **Таблиця зв'язку «терапевт — клієнт»**, яку заповнює утримання. Ні: прострочення відбувається без запису в базу
  (статус рахується від часу), тож зв'язок довелося б чистити фоновою задачею, а на Hobby її немає щохвилини.
- **Admin-клієнт на сервері з власною перевіркою ролі**. Ні: секретний ключ обходить RLS повністю, і одна помилка в
  перевірці відкриває всі картки; до того ж ключ довелося б тримати у Vercel.

## Наслідки

- Простіше: сторінки тонкі; нові екрани з картками безпечні за замовчуванням; правило перевіряється тестами бази.
- Складніше: функція з `now()` у політиці — тести мусять зсувати дані відносно поточного часу; кожен запит до
  `clients` для терапевта виконує підзапит до `holds` і `slots` (індекс `holds_client_idx` є).
- Якщо PM змінить «свій клієнт» (наприклад, додасть призначення терапевта у WS9), змінюється одна функція
  міграцією й тести AC-CARD-04, 05, 08.

## Як перевіряємо

- Тести бази на PGlite з усіма міграціями й RLS, назви з AC ID: `tests/db/client-access.test.ts` (AC-CARD-04, 05, 07,
  08, 09, 11), `tests/db/client-cards.test.ts` (AC-CARD-06, 10), `tests/db/therapist-visibility.test.ts` (AC-HOLD-20,
  21). Мутаційна перевірка: `clients_select … using (true)` у новій міграції валить AC-CARD-04, 05, 08, 09, 11; без
  умови ролі в `current_therapist_id()` падає AC-CARD-11 (таблиці — в описах PR задач, червоні прогони CI — там само).
- Правило в `.github/workflows/architecture.yml`, job «Секретний ключ лише на сервері» (`npm run check:boundary`):
  `SUPABASE_SECRET_KEY` у `src/` можна читати лише в `src/lib/supabase/admin.ts`, а admin-клієнт, що обходить RLS,
  — імпортувати лише в серверні дії (`actions.ts`, `route.ts`, `"use server"`), не в сторінки й не в клієнтські
  компоненти. У нас `admin.ts` немає взагалі, і ключ у `src/` не читає жоден файл; поява admin-клієнта — привід для
  нового ADR. Доказ, що правило ловить порушення, — червоний прогін у PR задачі 2.
